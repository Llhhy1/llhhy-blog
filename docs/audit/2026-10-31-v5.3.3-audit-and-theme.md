## 0. 一句话结论

- 代码质量仍在稳步提升（公开读路径大部分已统一走 `visible_posts_query()`，出站 HTTP 做了 IP pinning，上传有 magic-byte 校验，自动更新仍强制 Ed25519）。
- 但 **5.3.3 这个 tag 的 lint 门禁是红的**（10 条 ruff），且有一个**2FA 登出后残留状态**的真实绕过窗口、一个**译文可见性泄露**（正是这个项目反复复发的错误类别）。
- 你认为"界面不够好看、字体颜色怪"**不是审美问题**，是三套主题管线 + 1300+ 硬编码颜色 + 没有排版尺度造成的。代码里能直接量出 3.81:1 的正文灰色、深色代码块配浅色高亮主题等问题。
- 主题系统已经有一半（14 套预设 + OKLCH 暗色推导 + WCAG 求解器 + 后台主题中心）。**"像 WordPress 那样可换模板的主题商店"不建议做**；做成"主题包 2.0（token + 布局选项 + 访客自选）"性价比高得多，难度从"数月"降到"1~2 周"。

## 2. 安全与正确性问题（按可利用性排序）

> **状态**：P0-1、P0-2、P1-1 ~ P1-4 已由本 PR 修复；P2 中只有第 5 项（tags/site 计数）随批次 B 修复。P2 的 1-4 是「开放用户自定义主题」的前置，属于批次 D，**本轮未执行**；P2-6/P2-7 仍开放。

### P0-1　2FA 登出残留 `twofa_ok` → 共享浏览器可绕过第二因素

**位置**
- `myblog/admin/auth.py:79-82` 后台登出只 pop `user_id` / `admin`，**不清 `twofa_ok`**
- `myblog/api/auth.py:86-89` SPA 登出只 pop `user_id`
- `myblog/routes.py:142-145` 前台 `/logout` 是唯一清掉 `twofa_ok` 的（说明作者知道要清，只是没统一）
- `myblog/routes.py:126-129` 前台登录、`myblog/admin/auth.py:31-33` 后台登录都**不重置** `twofa_ok`
- `myblog/app.py:532-545` `enforce_twofa()` 直接信任 `session.get("twofa_ok")`

**场景**：已绑定 2FA 的用户在共用/网吧浏览器登录 → 通过 SPA 或后台登出 → 会话 Cookie 里 `twofa_ok=True` 仍在 → 知道密码的人在同一浏览器走 `/login` 或 `/admin/login`，闸门看到 `twofa_ok=True` 直接放行，**完全不需要 TOTP**。
前提是 `twofa_enabled` 打开（默认关）且攻击者能用同一浏览器；因此评为 High 而非 Critical，但这是实打实的 2FA 绕过。

**修法（最小）**
1. 所有登出统一 `session.clear()`（或至少同时 pop `twofa_ok` / `session_version`）。
2. 所有写 `session["user_id"]` 的登录路径，必须同时写 `session["twofa_ok"] = False`（`api/common.py:_login_user` 已经是正确范式，照抄）。
3. 更稳的做法：`twofa_ok` 绑定 `(user_id, session_version)`，版本一变即失效。
4. 把 `/admin/logout` 加入 `_TWOFA_ALLOW`，否则"只过了密码"的会话在后台点登出会被重定向到 `/twofa` 而不是退出。

**验收测试**：登录(2FA 已开) → 登出 → 只凭密码再登录 → 访问 `/admin/dashboard` 必须被 401/重定向到 2FA，不能放行。

### P0-2　`/admin/login` 完全没有限流 / 延迟

**位置**：`myblog/admin/auth.py:8-38`

前台 `/login`、`/api/auth/login` 都做了 `rate_limit(client_key(...), 10, 60)` + 登录延迟；**后台这个入口没有**，且成功日志写在 2FA 之前。
**后果**：可对任意账号（含超管）无限猜密码；用户名存在性可通过响应时间/日志侧信道探测。
**修法**：复用 `rate_limit` + `_login_delay()`，失败统一文案；成功日志移到第二因素之后。

---

### P1-1　译文组可见性泄露（"公开读路径忘了过滤"第 N 次复发）

**位置**
- `myblog/models.py:80-84` `Post.in_group()` 直接 `filter_by(translation_group=...)`，**无可见性过滤**
- `myblog/models.py:467-488` `hreflang_alternates()` 用它 → sitemap / RSS / OG 壳页都会吐出不可见译文的 slug 和 lang
- `myblog/api/posts.py:97-101` `GET /api/post/<slug>` 的 `translations[]` 同样不过滤

**后果**：一篇公开文章只要属于某个 `translation_group`，其私密/草稿/回收站译文的**标题与 slug** 会被匿名用户拿到；sitemap/feed 里也会出现这些 slug。
**修法**：`in_group(group, base_query=None)` 接受查询并默认用 `visible_posts_query()`；`hreflang_alternates` 增加 `user`/`visible_only` 参数；`post_detail` 的 `translations` 走同一过滤器。
**注意**：不要改 `visible_posts_query()` 的语义，只让这些调用点用上它。

---

### P1-2　匿名可强制刷新博客圈抓取 → 出站放大 / worker 占用

**位置**：`myblog/api/social.py:99-103`（`refresh=1` 直接 `force=True`）、`myblog/feed_agg.py:162-235`

匿名请求 `GET /api/feed/circle?refresh=1` 绕过 15 分钟缓存，同步抓取全部友链 RSS（单源 12s 超时），无频率限制。gunicorn 是 4×2 线程，重复请求可把 worker 占满，同时替站主去压友链站点。
**修法**：该端点限流；`refresh=1` 只允许超管或由定时任务触发（普通访客只读缓存）。

---

### P1-3　未配置 `EO_AUTH_KEY` 时无条件信任 `EO-Client-IP`

**位置**：`myblog/utils/net.py:152-170`（`if (not eo_key) or header匹配: 采纳 EO-Client-IP`）

代码注释已承认取舍：没配密钥时直连源站者可以轮换该头，从而绕过所有按 IP 的限流（登录 10/min、2FA、评论、上传）。
**修法（不破坏 EdgeOne 部署）**：没配密钥时，只有当 `remote_addr` 属于 EdgeOne 回源网段（或显式 `TRUSTED_PROXIES`）才采纳；否则用 `remote_addr`。README/deploy_guide 写清"要用 EO 真实 IP 必须配密钥"。

---

### P1-4　评论表情 GET 绕过文章可见性

**位置**：`myblog/api/reactions.py:71-86`

POST 走 `_readable_comment()`（已校验所属文章可见），但 GET 直接 `Comment.query.filter(Comment.id.in_(cids))`，会返回私密/草稿/回收站文章下评论的表情计数，等于存在性侧信道。
**修法**：GET 也走 `_readable_comment()`（批量版：先查评论，再用 `visible_posts_query()` 过滤 post_id）。

## 4. 为什么你会觉得"怪"（可量化的原因）

> **状态**：第 2、3、7 条已修；第 5 条修了元信息与标签两处；第 1、4、6 条为部分修复（见每条末尾）。三套主题管线仍未合并，是下一轮视觉升级的主要工作。

不是"设计品味"问题，是四条硬伤叠加：

1. **三套真相源**：SPA 用 `vue-frontend/src/styles/tokens.css` + 运行时 `theme_tokens`；后台用 `myblog/static/tokens.css`；登录/错误页用 `myblog/static/style.css`，且不加载 tokens。主题包换肤**永远到不了后台和登录页**。
2. **`--accent: var(--accent)` 自引用**：`vue-frontend/src/styles/global.css:6`、`myblog/static/style.css:5`。同一 `:root` 里后声明的自引用形成 CSS 循环 → `--accent` 变成 guaranteed-invalid；在 `initSite()` 完成前，所有 `var(--accent)` 都是坏的（首屏闪一下、失败时品牌色直接消失）。删掉这两行即可。
3. **代码块是深底配浅色高亮主题**：`global.css:436` 把 `pre` 背景写成 `#2d2d2d`，`PostView.vue:119` 却 `import "highlight.js/styles/github.css"`（浅色主题，文字 `#24292e`）。结果正文代码块是**深灰字压深灰底**，几乎不可读；`DocsView` 反而用 `github-dark`。这是"颜色怪"最直观的一处。
4. **排版没有尺度**：全站 **27 种 font-size、24 种 line-height**；正文 15px（SPA）/16px（登录、后台）/17px（文章页）；没有任何 web font，拉丁字母与中文分别落到 `Segoe UI` 和 `PingFang/雅黑`，同字号下字重与行高观感不一致。中文正文 15px + 1.7 行高本身偏挤。
5. **真实组合没做对比度检查**：测试只检查 token 对（`tests/test_wcag_contrast.py`），实际页面组合：
   - 文章元信息 `--text-faint` 13px 压白底 = **3.81:1**（`look.css:230`）
   - 标签文字压 chip 底 `#6a717f` / `rgba(120,120,128,.10)` 叠白 ≈ `#f2f2f2` = **4.38:1**（`look.css:530`，13px 需 4.5）
   - `#999` 压白底 = **2.85:1**（`global.css:393`、`style.css:37`）
   - 深色模式下 `StatsView.vue` 有 74 处颜色字面量、**零条 `[data-theme]` 覆盖**；`SquareView.vue:224` 的 `#1f1f1f` 在深色底上约 1.2:1。
6. **组件规则打架**：`look.css:43` 把按钮全局改成胶囊圆角，`global.css:853` 的天气组件按钮仍是 6px、主题切换按钮还用 `!important`；同屏出现方圆两种按钮。标签有 `#eef3fb` 与 `--ui-fill` 两套 chip。
7. **首页副标题被改成灰字**：`look.css:311` 把封面上的 `rgba(255,255,255,.96)` 换成 `--text-muted`，压在蓝色渐变/照片上，直接失去可读性。

**结论**：先把这 7 类修掉，观感会有质变；在这之前加再多主题包，也只是把"怪"换一种颜色。

## 5. 主题系统怎么升级：四档，建议只做前两档

### 档 0：设计系统收口（1~3 天，收益最大）

- 删自引用、统一 accent 默认值（`#1a73e8` vs `#196ddd` 二选一，建议 `#196ddd`）。
- 代码块统一 `github-dark`（或自定义深色 hljs 主题），`pre` 背景交给 `.hljs`。
- 修 7 类硬伤；把 `--text-faint` 13px 场景提到 4.5:1，或把元信息改 14px + `--text-muted`。
- 建立字号尺度（例如 12/13/14/16/18/22/28/36）并落成 `--text-xs/sm/base/lg/...`，禁止新代码写字面量。
- 把对比度测试从"token 对"扩到"真实组合"（白底 faint、chip、深色底、accent 上的白字）。
- 后台/登录页接入同一套 tokens。

### 档 1：访客自选主题（3~5 天，直接满足"用户定制化"）

- 新增访客主题选择器（抽屉/设置页）：14 套预设 + 亮/暗/跟随系统。
- 选择存 `localStorage`，不写 DB；加载时拉一次 `/api/theme`（已有公开接口），按 `pack_id` 用 `applyThemeTokens()` 应用对应 light/dark token。
- 后台加"允许访客自选主题"开关；关掉时只用站主主题。
- 不需要新表、不需要迁移，`/api/theme` 已经返回完整 presets（含 light/dark）。

### 档 2：主题包 2.0 + 策展式"主题商店"（1~2 周）

- 定义**纯数据**主题包格式（无代码）：
  ```json
  {
    "schema": 2,
    "id": "mist-blue",
    "name": "雾蓝",
    "version": "1.0.0",
    "tokens": { "light": {...}, "dark": {...} },
    "layout": { "hero": "split|full-bleed|minimal", "cards": "soft|flat|bordered",
                "nav": "top|side", "contentWidth": "narrow|wide", "typeScale": "compact|comfortable" },
    "assets": ["cover.webp"]
  }
  ```
- 服务端做 JSON Schema 校验 + token 白名单（严禁 `url()`、`</style>`、任意 CSS 值）。
- 前端把 `layout` 落成根节点 class（`data-theme-layout="hero-split cards-soft"`），用 CSS 变量控制版式；**不加载第三方 JS**。
- "商店"= 官方策展的 JSON 包列表（可放 GitHub raw / 本站静态目录），一键预览/安装；不做开放上传。
- 这就是 WordPress"主题目录"的**安全等价物**，但换不来"任意改模板"。

### 档 3：WordPress 式代码主题（不建议）

WordPress 主题 = 可执行 PHP 模板 + hooks，能改任意结构和逻辑。这个项目的前台是**编译后的 Vue SPA**：

- 要让主题改模板，只能 (a) 运行时加载第三方 Vue 组件/JS → 等于把任意代码执行权交给主题作者（供应链攻击、CSP 失效、版本兼容地狱）；或 (b) 恢复服务端模板渲染 → 与 v3.18.6 已退役的 SSR 路线冲突，又会把 SEO 通道搞回去。
- 单人维护的项目做"开放主题市场"，审核成本远高于收益。
- **建议明确不做**；如果一定要"更像 WP"，用档 2 的 `layout` 插槽把版式差异做足即可。
